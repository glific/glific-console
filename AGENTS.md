# Glific Console: agent guide

The new Glific frontend (2.0). Vite + React 19 + TypeScript (strict), Tailwind v4 + shadcn/ui (Radix), React Router,
TanStack Query, i18next. Single app, pnpm. Stack rationale: `docs/adr/0001-stack.md`.

## Commands

| Command                            | What it does                                                                                 |
| ---------------------------------- | -------------------------------------------------------------------------------------------- |
| `pnpm dev`                         | Dev server with MSW mocks (`.env.development`)                                               |
| `pnpm check`                       | typecheck + lint + DS lint + unit/component tests. **Must pass before you say you're done.** |
| `pnpm typecheck`                   | `tsc -b`                                                                                     |
| `pnpm lint` / `pnpm lint:fix`      | Biome check (format, lint, imports, DS rules)                                                |
| `pnpm lint:ds`                     | Design-system rules only, plus the fixture self-test proving each rule fires                 |
| `pnpm test` / `pnpm test:coverage` | Vitest Browser Mode (Chromium). Coverage gate: 80% on `src/components`                       |
| `pnpm test:e2e`                    | Playwright flows + axe a11y (starts its own dev server)                                      |
| `pnpm test:visual`                 | Visual regression. Baselines come only from `pnpm test:visual:update` (runs in Docker)       |
| `pnpm build` / `pnpm size`         | Production build / bundle budgets (`.size-limit.json`)                                       |
| `pnpm changeset`                   | Record a user-facing change                                                                  |

## Layout

```
src/components/ui/     shadcn components: owned code, customised in place
src/components/        app-level composed components (EmptyState, ErrorState, PageHeader, Spinner)
src/features/<name>/   feature code: components, hooks, api.ts, types.ts, tests, index.ts (public surface)
src/routes/            route tree (router.tsx), layout, pages, 404, error boundary
src/lib/               api-client, query-client, env/config, i18n, storage, utils (cn)
src/styles/tokens.css  ALL design tokens; tokens.ts is the manifest the catalog reads
src/locales/en.json    UI strings
src/mocks/             MSW handlers (dev + tests)
src/test/              test helpers: renderWithProviders, renderRoute, expectNoA11yViolations, MSW worker
e2e/                   Playwright: flows/, a11y/, visual/
tools/ds-lint/         GritQL rules + fixtures for the design-system guardrails
docs/adr/ docs/specs/  decisions and feature specs
```

## UI rules (enforced by `pnpm lint:ds`)

- **Compose from `@/components/ui` and `@/components` only. Never inline one-off styles.** If a component or
  variant you need is missing, **stop and propose it** (name, variants, where it's used) instead of building a
  local one.
- Need a different look for an existing component? Add a **variant** (cva) to the ui component; don't wrap it in a
  new `FooButton`/`FooInput`. Composing a feature dialog (`CreateContactDialog` from `@/components/ui/dialog`) is fine.
- Colours: semantic tokens only (`bg-primary`, `text-muted-foreground`, `bg-success`, `text-warning-foreground`, ...).
  Raw colour values (hex/rgb/hsl/oklch) live **only** in `src/styles/tokens.css`.
- No arbitrary Tailwind values (`p-[13px]`, `text-[15px]`). Arbitrary _variants_ (`data-[state=open]:`) are fine.
- Type scale: `text-display | title | heading | subheading | body | body-sm | caption`.
  Spacing: `p-page`, `gap-section`, `gap-stack`, `gap-inline`, plus Tailwind's numeric scale.
- No `style={...}` outside `src/components/ui`. Allowlist: add the file as a `!path` to the `no-inline-style`
  plugin `includes` in `biome.json`, with a one-line reason in the PR.
- No `radix-ui` / `@radix-ui/*` imports outside `src/components/ui`. Import `cn` from `@/lib/utils`, never from `cn`.
- Every screen handles **loading, empty, error** (Skeleton/Spinner, EmptyState, ErrorState).
- All user-facing text goes through `t()` (`useTranslation`) with keys in `src/locales/en.json`.

## Tokens

Add or change tokens in `src/styles/tokens.css` (primitive → semantic → `@theme inline`) **and**
`src/styles/tokens.ts`. `src/styles/tokens.test.ts` fails if they drift. The app is light-only (the 2.0 designs
have no dark theme); ignore shadcn's `dark:` classes rather than adding `.dark` tokens.

## shadcn components are owned code

`src/components/ui` was generated by the shadcn CLI and has since been customised (imports `cn` from
`@/lib/utils`, translated labels, a11y fixes). Add new ones with `pnpm dlx shadcn@<pinned> add <name>`.
When re-running the CLI over an existing component, **review the diff and keep our customisations**: never
accept an overwrite blindly. The `form` registry item is empty in this style; use `field` with your own state.

## Data

- Server state lives in TanStack Query hooks in `features/<name>/api.ts` with a key factory (`contactKeys`).
- HTTP goes through `apiClient` (`src/lib/api-client.ts`). Never call `fetch` from components.
- Add an MSW handler in `src/mocks/handlers.ts` for every endpoint you use, so dev and tests work offline.
- Env vars: add to `src/lib/env.ts` (typed + validated) and `.env.example`. Never read `import.meta.env` elsewhere.

## Tests

- Component tests: `*.test.tsx` next to the component. Use `renderWithProviders`, Testing Library queries by role,
  `userEvent` from `vitest/browser`, and `expectNoA11yViolations()` (scope it to the open overlay for modals).
  Cover: render, variants, keyboard interaction, axe.
- Feature tests: drive states with `worker.use(http.get(...))` from `@/test/msw`.
- E2E: `e2e/flows` for user journeys, `e2e/a11y` for axe per page, `e2e/visual` tagged `@visual`.

## Verifying a change

1. `pnpm check` passes.
2. UI change: `pnpm test:e2e` passes. If visuals changed intentionally, regenerate with `pnpm test:visual:update`.
3. Conventional Commit messages (`feat(contacts): ...`); add a changeset for user-facing changes.
